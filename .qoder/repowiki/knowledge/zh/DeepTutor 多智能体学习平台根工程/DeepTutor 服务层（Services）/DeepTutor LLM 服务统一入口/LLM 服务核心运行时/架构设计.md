模块以 `factory.py` 暴露顶层 `complete/stream/fetch_models` 函数作为统一入口，内部通过 `_resolve_call_config` 解析 `model/api_key/base_url/binding` 并借助 `provider_registry` 确定目标 provider spec；再由 `provider_factory.get_runtime_provider` 按 `backend`（openai_codex / github_copilot / azure_openai / anthropic / openai_compat）懒加载具体实现，并以事件循环 + 进程级有序字典维护最多 2 个 provider 实例的连接池，避免重复创建 SDK 客户端。

- `provider_core/base.py` 定义 `LLMProvider` 抽象接口（`chat/chat_stream/chat_with_retry/chat_stream_with_retry`），内置指数退避重试、瞬态错误识别以及 Stage-2 图片回退（非已知视觉模型失败时自动剥离图片重试）。
- `provider_core/openai_compat_provider.py` 基于官方 `openai.AsyncOpenAI` 适配所有 OpenAI 兼容端点，并通过 `provider_core/openai_responses/` 子包完成 responses API 转换与流消费；`azure_openai_provider`、`anthropic_provider`、`github_copilot_provider`、`openai_codex_provider` 各自处理特定后端差异。
- `providers/routing.py` 是遗留桥接层，根据 `is_local_llm_server` 在 `cloud_provider`/`local_provider` 之间路由，保持旧 API 稳定。
- `config.py` 通过 `ContextVar` 支持异步上下文内 scoped 配置，并在模块导入时提前设置 `OPENAI_*` 环境变量以兼容下游 SDK；`LLMConfig` 数据类承载 model、binding、provider_name、provider_mode、reasoning_effort 等字段。
- `client.py` 提供面向历史代码的 `LLMClient` 单例及 `get_llm_client/reset_llm_client`，内部委托给 factory。
- 横切关注点：`capabilities.py` 声明各 provider/model 的能力开关（vision/tools/response_format/streaming）、`error_mapping.py` 将底层异常映射为统一 `LLMError` 族、`multimodal.py` 负责图像消息拼装、`traffic_control.py`/`telemetry.py`/`executors.py` 提供限流与遥测。
- 依赖方向：上层 `factory` → `provider_factory` → `provider_core/*`；`providers/*` 仅用于兼容层；配置与能力表被多处共享引用。

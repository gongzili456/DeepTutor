## 1. 使用的系统与方法

仓库是一个混合语言项目，采用三种互补的依赖声明方式：

- **Python（后端 / CLI）**：以 `pyproject.toml` 为入口，使用 setuptools 构建；通过 `deeptutor/modules/manifests/*.json` 作为“模块清单”（module manifest）集中声明每个子模块的运行时依赖与模块间依赖关系；由 `scripts/sync_module_requirements.py` 将清单同步生成 `requirements/core.txt`、`requirements/modules/*.txt`、`requirements/full.txt` 等 pip requirements 文件；再由顶层 `requirements.txt` 引用 `requirements/full.txt`。
- **TypeScript（Web / chat-engine / desktop）**：各自维护独立的 `package.json` + `package-lock.json`，使用 npm 包管理器；未使用 monorepo 工具（无 `pnpm-workspace.yaml` / `lerna.json` / `turbo.json`），各子包独立安装。
- **打包产物**：`scripts/build_modules.py` 根据 manifest 动态拼装临时 `pyproject.toml`，调用 `pip wheel --no-deps --no-build-isolation` 为每个模块产出独立 wheel，并在构建后校验不同 wheel 之间不存在路径重叠。

未发现私有 PyPI 源或 `PIP_INDEX_URL`/`PYPI_URL` 配置，也未发现 vendored 第三方源码目录。所有第三方库均从公共 PyPI/npm registry 拉取。

## 2. 关键文件

- `pyproject.toml`：定义 core 依赖、`requires-python = ">=3.11,<3.15"`、`[tool.deeptutor.optional-dependencies]` 中的可选 profile（如 `server`、`matrix`、`dev`、`full` 等），以及 Black/Ruff/pytest/mypy/bandit 等工具配置。
- `deeptutor/modules/manifests/*.json`：每个模块一份清单，包含 `id`、`distribution`、`requires`、`requirements`、`capabilities`、`tools`、`routes`、`entry_points` 等字段。`core.json` 是根模块，其他模块通过 `requires` 指向其依赖模块。
- `scripts/sync_module_requirements.py`：读取 manifests 并生成 `requirements/core.txt`、`modules/<name>.txt`、`cli.txt`、`server.txt`、`full.txt`；支持 `--check` 模式在 CI 中校验这些文件是否过期。
- `scripts/build_modules.py`：为每个模块生成临时 `pyproject.toml` 并执行 `pip wheel`，同时检查 wheel 之间的文件覆盖冲突。
- `requirements.txt` → `requirements/full.txt` → `requirements/modules/*.txt`：pip 依赖链，顶层仅 `-r requirements/full.txt`。
- `web/package.json` + `web/package-lock.json`：Next.js 前端依赖，声明 `overrides` 强制 `epubjs` 下的 `@xmldom/xmldom` 版本。
- `packages/chat-engine/package.json` + `package-lock.json`：共享 TypeScript 聊天引擎库。
- `apps/desktop/package.json` + `package-lock.json`：Electron 桌面应用，声明 `engines.node >= 22`，并通过 `overrides` 锁定 `@electron/asar` 下的 `glob`/`minimatch`。

## 3. 架构与约定

### Python 模块化依赖模型

- 每个模块在 `deeptutor/modules/manifests/<name>.json` 中声明自己的 `requirements`（直接 pip 依赖）和 `requires`（对其他 DeepTutor 模块的依赖）。`core.json` 的 `requires` 为空数组，是所有模块的根。
- `sync_module_requirements.py` 把 `core.txt` 作为基础，其他模块文件以 `-r ../core.txt` 开头，并以 `-r <dependency>.txt` 形式引入所依赖模块的文件，从而形成树状 requirements 组合。
- `full.txt` 聚合除 `core`、`renderer-manim` 以及 `parser-*` 之外的所有模块文件（注释说明 parser 系列被排除）。
- `build_modules.py` 在构建 wheel 时，对非 core 模块追加 `deeptutor=={version}` 以及 `requires` 列表中每个模块的 `distribution=={version}` 依赖，确保已发布 wheel 之间版本严格对齐。
- `pyproject.toml` 中的 `[tool.deeptutor.optional-dependencies]` 定义了可选功能 profile（如 `server`、`matrix`、`math-animator`、`rag-lightrag`、`guard`、`dev`、`all`、`full` 等），其中许多 profile 通过 `deeptutor-<feature>=={version}` 的形式引用同版本的独立 wheel，实现“核心包 + 可选扩展包”的解耦。
- `requires-python = ">=3.11,<3.15"` 在 pyproject 顶层统一约束解释器范围；部分依赖（如 `graphrag`、`rag-rerank`）通过 `; python_version < '3.14'` 条件标记进一步收窄。

### Web 端依赖

- `web/package.json` 使用较宽松的语义版本（`^` 前缀），但通过 `package-lock.json` 锁定实际解析结果。
- 使用 `overrides` 字段强制解决已知漏洞或不兼容的子依赖（例如 `epubjs` 下的 `@xmldom/xmldom`）。
- `packages/chat-engine/package.json` 通过 `engines.node >= 22` 声明 Node 最低版本。
- `apps/desktop/package.json` 固定 Electron 主进程版本（`electron: 45.1.0`），并通过 `overrides` 锁定 `@electron/asar` 传递依赖的 `glob` 与 `minimatch`。

### 构建与发布

- `scripts/build_modules.py` 生成的临时 `pyproject.toml` 使用 `setuptools.build_meta` 后端，并为每个模块设置 `namespaces = true`，使多个 `deeptutor.*` 命名空间包可以共存于同一个 site-packages。
- 构建完成后会遍历 zip 中的文件路径，若同一路径出现在两个 wheel 中则抛出 `Wheel overlap` 错误，以此强制模块间文件不重叠。

## 4. 约定与约束

- **Python 依赖的唯一权威来源是 manifests**：`requirements/core.txt`、`requirements/modules/*.txt`、`requirements/full.txt` 顶部注释写明 `# Generated by scripts/sync_module_requirements.py; edit module manifests.`，禁止手动编辑这些 requirements 文件。
- **CI 可校验 requirements 是否过期**：`sync_module_requirements.py` 支持 `--check` 模式，当生成的内容与磁盘不一致时返回非零退出码（`raise SystemExit(f"Stale dependency file: {path}")`），可用于 CI 门禁。
- **模块间依赖必须通过 manifest 的 `requires` 声明**：`build_modules.py` 在组装 wheel 依赖时会读取 `module["requires"]`，未在清单中声明的模块依赖不会被注入到最终 wheel 的 `dependencies` 中。
- **wheel 构建禁止依赖解析**：`pip wheel --no-deps --no-build-isolation` 表明模块 wheel 不包含自身依赖，只声明依赖元数据；运行时依赖由安装方（Docker、用户环境）提供。
- **可选依赖通过 profile 而非硬编码**：新增可选能力应在 `pyproject.toml` 的 `[tool.deeptutor.optional-dependencies]` 中添加 profile，并在对应模块 manifest 的 `optional` 字段中声明（参考 `core.json` 中 `optional` 字段的存在）。
- **Python 解释器版本上限**：`requires-python = ">=3.11,<3.15"` 显式阻止未来 Python 版本在未验证时被宣传；部分重型依赖（`graphrag`、`sentence-transformers`）额外要求 `< 3.14`。
- **Web 端依赖通过 npm lockfile 锁定**：`web/package-lock.json`、`packages/chat-engine/package-lock.json`、`apps/desktop/package-lock.json` 分别锁定三个子项目的实际依赖树。
- **存在已知脆弱子依赖的 override 策略**：`web/package.json` 与 `apps/desktop/package.json` 都使用 `overrides` 字段强制升级特定子依赖版本，而不是修改上层包的版本。
- **未发现私有注册表配置**：仓库中未出现 `PIP_INDEX_URL`、`PYPI_URL`、`index-url`、`extra-index-url`、`.npmrc` 等私有源配置，所有依赖均来自公共 PyPI 与 npm registry。
- **Docker 镜像依赖来源**：顶层 `Dockerfile` 与 `compose*.yml` 通过 `requirements.txt` 安装依赖，间接继承 `requirements/full.txt` 的模块组合。
